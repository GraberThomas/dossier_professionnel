\section{Présentation du projet}

Le projet \terme{s123} constituait le sujet initial de mon alternance au Shom. Il m'a été présenté sous la forme d'un objectif volontairement large : concevoir une « base de données \terme{s123} » capable d'accueillir les renseignements relatifs aux radiosignaux aujourd'hui répartis dans plusieurs ouvrages et sources de données.

Ce sujet s'inscrivait dans la transition du secteur hydrographique vers l'écosystème \terme{s100} de l'Organisation hydrographique internationale (OHI). \terme{s100} définit un cadre commun à des spécifications de produits de données destinés aux utilisateurs finaux : chaque produit S-1xx décrit un type de données, sa structure et les règles nécessaires à son échange et à son exploitation. Les cartes électroniques de navigation, historiquement produites selon S-57, doivent ainsi évoluer vers S-101 ; \terme{s123} définit pour sa part le produit consacré aux services radio maritimes. Mon travail ne portait donc pas sur les cartes elles-mêmes, mais sur la structuration des renseignements radio dans ce nouvel écosystème.

Le besoin répondait également à une limite de l'existant : une part importante de l'information radio est aujourd'hui peu structurée et portée directement par les ouvrages destinés à la lecture humaine. L'objectif à plus long terme est de disposer d'une donnée structurée selon le standard international \terme{s123}, afin de pouvoir la contrôler, la réutiliser et produire des jeux de données conformes sans dépendre uniquement de la mise en forme éditoriale des ouvrages.

Le projet a connu plusieurs étapes de conception. J'ai d'abord étudié une transposition directe de \terme{s123} dans une base relationnelle, puis expérimenté différentes manières de parcourir et transformer les catalogues XML. Ces travaux m'ont progressivement conduit vers une architecture plus générique, organisée autour du Feature Catalogue \terme{s100}. Le \terme{poc} final associe un modèle relationnel générique, un parseur XML fondé sur les \terme{xsd}, des seeders spécialisés pour le peuplement de PostgreSQL et une \terme{api} \terme{rest} de consultation développée avec FastAPI.

Au moment de la rédaction de ce dossier, l'analyse métier, le méta-modèle de catalogue, le parsing XML, le chargement de PostgreSQL et l'\terme{api} de consultation sont fonctionnels dans le cadre du \terme{poc}. Le stockage des instances métier, leur saisie, leur validation complète et les exports S-1xx restent à développer. Le projet ne constitue donc pas encore une application de production, mais il couvre déjà la chaîne allant d'un Feature Catalogue XML jusqu'à son interrogation par \terme{api}.

J'ai modélisé la version 1.0 dans Modelio, puis représenté une partie du schéma dans pgModeler. L'évolution importante entre \terme{s123} 1.0 et 1.1 a rendu une partie du travail obsolète avant même l'achèvement de la base, sans garantir la stabilité des versions suivantes.

\section{Conception d'un méta-modèle \terme{s100}}

\subsection{Séparer la définition du modèle et les données métier}

À partir de ce constat, j'ai conçu un méta-modèle destiné à représenter les concepts communs des Feature Catalogues \terme{s100} plutôt qu'une version figée de \terme{s123}. La solution sépare deux niveaux. Le premier, réalisé dans le \terme{poc}, décrit le catalogue : types d'entités et d'information, attributs, associations, rôles, cardinalités, contraintes et héritage. Le second doit accueillir les futures instances métier et leurs valeurs.

Au lieu de créer une table par classe \terme{s123}, la base enregistre donc la description des classes. Elle peut définir qu'un type d'entité possède un attribut obligatoire, multivalué ou limité à une énumération. Les futures instances pourront ensuite être construites et validées à partir de cette description.

La partie consacrée aux données s'inspire du principe Entity--Attribute--Value, sans se réduire à trois colonnes génériques. Le schéma conserve explicitement les types, associations, héritages, cardinalités, unités et contraintes décrits par \terme{s100}. Cette approche cherche ainsi un compromis entre flexibilité et intégrité.

\section{Du Feature Catalogue XML à PostgreSQL}

\subsection{Génération du modèle Python et parsing XML/\terme{xsd}}

Les Feature Catalogues sont des documents XML décrits par les \terme{xsd} \terme{s100}. Plutôt que d'écrire manuellement toutes les classes Python correspondant à cette structure, j'ai utilisé \texttt{xsdata} pour les générer à partir des schémas officiels.

Il faut distinguer deux étapes. Lors du développement, \texttt{xsdata} génère les dataclasses Python depuis les \terme{xsd}. À l'exécution, son \texttt{XmlParser} lit un Feature Catalogue XML et instancie ces classes. Un objet de type \texttt{S100FcFeatureCatalogue} constitue alors la racine d'un graphe contenant les attributs, rôles, associations, types, multiplicités et références du catalogue.

Le parseur applique également un prétraitement limité aux espaces de noms avant de construire l'objet racine. Le reste de l'application peut ensuite travailler sur des objets Python typés plutôt que parcourir directement des balises XML.

\begin{lstlisting}[language=Python,caption={Parsing d'un Feature Catalogue en objet Python},label={lst:s123-parser}]
def get_feature_catalogue(file_path: str) -> S100FcFeatureCatalogue:
    with open(file_path, "rb") as f:
        xml_str = f.read()

    config = ParserConfig()
    context = XmlContext()
    parser = XmlParser(
        context=context,
        config=config,
        handler=LxmlEventHandler,
    )

    return parser.from_bytes(xml_str, S100FcFeatureCatalogue)
\end{lstlisting}

Cette séparation entre schéma, classes générées et instances XML était importante pour limiter le code écrit à la main et conserver une correspondance forte avec \terme{s100}.

\subsection{Peuplement de la base avec des seeders spécialisés}

Pour persister le catalogue, j'ai organisé le chargement autour d'un \texttt{FeatureCatalogueSeeder}. L'objet racine lui est transmis, puis il orchestre PostgreSQL et délègue chaque catégorie à un seeder spécialisé : attributs, rôles, associations, types et liaisons.

La chaîne d'exécution principale peut être résumée par les deux instructions suivantes :

\begin{lstlisting}[language=Python,caption={Enchaînement du parser et du seeder},label={lst:s123-parser-seeder}]
feature_catalogue = get_feature_catalogue(S123_FILE_URL)
FeatureCatalogueSeeder(feature_catalogue).seed(db_connection)
\end{lstlisting}

Les insertions sont réalisées dans une transaction afin d'éviter de conserver un catalogue partiellement chargé. Leur ordre est déterminant : les attributs et rôles doivent par exemple exister avant certaines liaisons, et les super-types avant leurs descendants. Un dictionnaire de correspondance entre les codes du catalogue et les identifiants créés en base permet de résoudre les références pendant le chargement.

L'héritage nécessite un traitement supplémentaire. Les types peuvent référencer un super-type par son code ; un tri topologique détermine donc un ordre compatible avec ces dépendances. Les éléments sans parent sont insérés en premier, puis leurs descendants. La présence d'un cycle provoque une erreur plutôt qu'une insertion incohérente.

\subsection{Expérimentation d'un patron Visiteur}

Au cours du développement, j'ai également étudié la manière d'ajouter des traitements transversaux au graphe d'objets produit par \texttt{xsdata}. Le problème venait du caractère généré des classes : modifier manuellement \texttt{S100FcFeatureType}, \texttt{S100FcInformationType} ou les autres classes aurait rendu ces ajouts fragiles, puisqu'une nouvelle génération depuis les \terme{xsd} pouvait les écraser.

J'ai donc prototypé un patron Visiteur. Une interface abstraite \texttt{Visitor} déclarait des opérations correspondant aux principales catégories du modèle. J'ai également développé un mécanisme permettant d'ajouter dynamiquement une méthode \texttt{accept} aux classes concernées. Le nom de la classe était converti vers la méthode \texttt{visit\_*} correspondante ; par exemple, \texttt{S100FcFeatureType} était associé à \texttt{visit\_s100\_fc\_feature\_type}. Un traitement spécifique était prévu pour les énumérations et un mécanisme générique pouvait servir de solution de repli.

Cette expérimentation répondait à un vrai besoin de découplage entre le code généré et les traitements susceptibles de lui être appliqués. Elle ouvrait des usages tels que la validation, l'inspection, le diagnostic ou la préparation d'un export sans modifier les dataclasses générées.

En revanche, ce mécanisme n'a pas été retenu dans le chemin principal du \terme{poc} final. La persistance repose sur les seeders spécialisés, qui expriment directement les règles de correspondance avec PostgreSQL, l'ordre des dépendances et les identifiants nécessaires aux relations. Le Visiteur reste donc un travail exploratoire de conception, réutilisable pour de futurs traitements transversaux, mais il ne faut pas le confondre avec le mécanisme effectivement utilisé pour charger la base.

\section{Rendre le modèle relationnel exploitable}

\subsection{Des vues SQL adaptées à la lecture}

Le modèle relationnel a été conçu en priorité pour préserver l'intégrité du catalogue. Cette normalisation devient cependant coûteuse lorsqu'un client veut récupérer un objet complet. Un Feature Type, par exemple, combine des informations provenant de \texttt{feature\_type}, \texttt{item\_info}, de son éventuel parent et de plusieurs tables de liaisons.

Pour éviter de reconstruire ce graphe dans chaque requête Python, j'ai enrichi PostgreSQL avec des vues dédiées à la consultation. Le schéma final comprend notamment des vues pour les attributs complexes, les associations, les Information Types et les Feature Types. Elles utilisent les fonctions JSON de PostgreSQL afin d'agréger les relations et de fournir à l'\terme{api} une représentation déjà structurée.

Cette approche ne transforme pas la base en stockage documentaire : les données restent normalisées dans les tables relationnelles. Le JSON est utilisé comme format d'agrégation à la lecture, pour rapprocher le résultat SQL de la structure attendue par les objets applicatifs et les réponses HTTP.

\subsection{Recherche globale dans le catalogue}

Le \terme{poc} final ajoute également une recherche textuelle transversale. Les informations communes et les valeurs listées disposent d'un champ \texttt{tsvector} calculé à partir de leur nom ou libellé et de leur définition. Une vue \texttt{v\_full\_search} regroupe les principales catégories du catalogue : attributs, Feature Types, Information Types, associations, rôles et valeurs listées.

L'\terme{api} construit ensuite une requête \texttt{tsquery}, calcule un score avec \texttt{TS\_RANK} et utilise \texttt{TS\_HEADLINE} pour mettre en évidence les correspondances. La recherche peut être filtrée selon le type d'objet recherché. Cette fonctionnalité montre que la base n'est pas seulement destinée à importer un catalogue, mais également à l'explorer.

\section{Développement de l'\terme{api} \terme{rest} de consultation}

\subsection{Architecture retenue}

La dernière étape majeure du \terme{poc} a été le développement d'une \terme{api} \terme{rest} avec FastAPI. Elle expose la structure du catalogue sans imposer aux applications clientes un accès direct à PostgreSQL.

La consultation utilise \texttt{asyncpg} avec un pool de connexions asynchrones. Ce choix est distinct de la chaîne d'import, qui utilise \texttt{psycopg} dans un traitement batch synchrone. Les deux composants répondent donc à des usages différents : ingestion ponctuelle d'un catalogue d'un côté, consultation concurrente via HTTP de l'autre.

Le code de l'\terme{api} est organisé en plusieurs responsabilités :

\begin{itemize}
    \item les \textit{routers} déclarent les endpoints, leurs paramètres, les erreurs HTTP et les modèles de réponse ;
    \item les \textit{repositories} exécutent les requêtes SQL asynchrones ;
    \item les \textit{mappers} transforment les lignes et agrégats JSON renvoyés par PostgreSQL en objets applicatifs ;
    \item les schémas Pydantic décrivent et valident les contrats exposés par l'\terme{api} ;
    \item les vues PostgreSQL préparent les graphes complexes nécessaires aux réponses.
\end{itemize}

Cette séparation évite de mélanger le protocole HTTP, l'accès aux données et la transformation des résultats. Les modèles Pydantic servent également à générer automatiquement le contrat OpenAPI de l'\terme{api}.

\subsection{Fonctionnalités exposées}

L'\terme{api} permet de consulter les attributs simples ou complexes, d'obtenir le détail d'un attribut avec son type, son unité, ses contraintes et ses valeurs listées, ainsi que de rechercher les objets qui utilisent directement cet attribut. Des endpoints exposent également les Feature Types, Information Types, Feature Associations, Information Associations, rôles et valeurs listées.

Une recherche globale permet de retrouver un élément du catalogue à partir d'un texte et de filtrer le résultat selon sa catégorie. Plusieurs endpoints renvoient aussi le schéma JSON des modèles Pydantic avec \texttt{model\_json\_schema}. Cette fonctionnalité constitue une première brique pour de futurs clients capables de découvrir dynamiquement les structures manipulées.

L'\terme{api} reste orientée vers la lecture du catalogue. Les endpoints de création et de modification d'instances métier, les extensions propres au Shom et la production d'exports conformes ne sont pas réalisés. Elle doit donc être présentée comme une \terme{api} de consultation fonctionnelle dans le cadre du \terme{poc}, et non comme une application de production finalisée.

\section{Généricité et essais sur d'autres S-1xx}

Le modèle ne dépend pas des objets propres aux services radio : il représente les concepts communs d'un Feature Catalogue \terme{s100}. Le même parseur et les mêmes seeders peuvent donc traiter d'autres catalogues compatibles avec les \terme{xsd} pris en charge.

Le script de travail contient plusieurs catalogues, notamment S-101, S-104, S-111, \terme{s123}, S-124 et S-129. Dans l'état final conservé dans mon dossier de travail, le script est configuré pour charger un catalogue S-101 avec le même parseur, le même modèle Python et les mêmes seeders que ceux utilisés pour \terme{s123}. Cette vérification montre que la généricité ne reste pas seulement théorique sur le plan technique ; elle ne constitue toutefois pas une validation métier de S-101 par un spécialiste de ce produit, mais uniquement un essai de compatibilité du mécanisme de chargement avec son Feature Catalogue.

La coexistence simultanée de plusieurs catalogues dans une même base doit également être consolidée. Il faudra rattacher chaque définition à un produit et à une version, puis adapter certaines contraintes d'unicité afin d'éviter les collisions de codes entre catalogues.

\section{Validation du \terme{poc}}

Les tests restent principalement exploratoires. La transaction protège contre une insertion partielle et le tri topologique détecte les cycles d'héritage. \section{Limites et perspectives}

Le \terme{poc} démontre la faisabilité de l'architecture, mais il conserve plusieurs limites. Le méta-modèle réduit l'impact des évolutions des catalogues ; une modification des \terme{xsd} communs peut néanmoins nécessiter de régénérer les classes et d'adapter certains seeders ou éléments du schéma.

La partie d'import est également plus avancée que la gestion du cycle de vie des données métier. Les sources historiques sont encore conçues pour une lecture humaine et leur transformation ne pourra pas être entièrement automatisée sans qualification par les spécialistes du GAN.

Enfin, le code final contient encore plusieurs traces du caractère exploratoire du projet : conventions de nommage à homogénéiser, quelques éléments de débogage et une gestion du cycle de vie du pool de connexions FastAPI à corriger avant toute industrialisation. Ces défauts ne remettent pas en cause le principe validé par le \terme{poc}, mais ils justifient de ne pas le présenter comme prêt pour la production.

Les prochaines étapes identifiées sont les suivantes :

\begin{itemize}
    \item ajouter la gestion explicite des catalogues, produits et versions ;
    \item finaliser le modèle des instances métier et de leurs valeurs ;
    \item compléter l'\terme{api} de consultation par des endpoints de création et de modification des instances ;
    \item exploiter les schémas du catalogue pour générer des formulaires de saisie ;
    \item tester la saisie d'objets \terme{s123} avec les spécialistes métier ;
    \item définir les extensions propres au Shom sans perdre la traçabilité de leur origine ;
    \item produire puis valider des exports \terme{s123} ;
    \item automatiser les tests du parseur, des seeders, des contraintes de catalogue et de l'\terme{api} ;
    \item réutiliser éventuellement le travail sur le Visiteur pour des traitements transversaux de validation, d'inspection ou d'export.
\end{itemize}

\section{Bilan critique et apports professionnels}

Ce projet m'a placé face à une demande ambitieuse, formulée avant la stabilisation du besoin. La difficulté principale a été de comprendre simultanément un domaine métier nouveau, une norme complexe et la manière de construire une architecture suffisamment durable pour ne pas reproduire le modèle à chaque évolution.

La première modélisation directe à 73 tables, bien qu'abandonnée, a joué un rôle important : elle a objectivé les limites d'une transposition stricte du format d'échange. Le passage à 18 tables traduit surtout un changement de niveau d'abstraction. Le \terme{poc} final ne stocke plus une photographie rigide de \terme{s123} ; il représente les concepts nécessaires à la description d'un Feature Catalogue \terme{s100}.

Je suis particulièrement satisfait de cette orientation, car le parseur, le modèle Python généré, les seeders, le modèle relationnel, les vues de consultation et l'\terme{api} sont construits autour de cette structure commune plutôt que d'une liste figée d'objets radio. Le chargement exploratoire d'un catalogue S-101 avec la même chaîne constitue pour moi un indice concret de la généricité technique du choix, sans valoir validation fonctionnelle de S-101.

Le travail sur le patron Visiteur reste également un apport important, mais d'une autre nature. Il correspond à une expérimentation de conception visant à ajouter des comportements autour d'un modèle généré sans modifier celui-ci. Son absence du chemin d'exécution final montre aussi qu'un patron n'a d'intérêt que s'il répond réellement à la responsabilité considérée : pour la persistance relationnelle, les seeders spécialisés étaient plus adaptés.

Enfin, le développement de l'\terme{api} a donné une finalité concrète au modèle. Les vues SQL, les repositories, les mappers et les schémas Pydantic transforment une structure relationnelle normalisée en contrat de consultation exploitable par un client. Le projet m'a ainsi fait progresser en modélisation, parsing XML/\terme{xsd}, génération de classes, architecture Python, patrons de conception, PostgreSQL et FastAPI. Il m'a surtout appris qu'une décision d'architecture consiste autant à choisir le bon niveau d'abstraction qu'à choisir une technologie.
